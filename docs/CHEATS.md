# Cheat catalog

Every known way a Lean (or computational) result can look verified without being so, and which layer of `vl`
catches it. It describes this version of `vl` (CHANGELOG.md); `*` marks what is planned and not built.

## Purpose

A green build is not a verified result. A proof can be complete and the claim still empty, weaker than the prose,
or about different definitions; a checker can be fooled, bypassed or misread; a record can say more than the check
did. This catalog lists each such mode once, with a concrete form, the `vl` layer meant to catch it, the planted
case that proves the detector can fail, and a public source or "observed in practice". It is the reference for
the planted suite and for the `vl-referee` skill.

R7 also covers revision and author confusion in meaning reviews: new fidelity reviews reject an explicit
historical item revision, saved full-meaning reviews are rejected when their available item blob contradicts
their saved meaning, and self-review compares the reviewer with the trusted author. The planted historical
request, disabled revision guard, inconsistent earlier record and valid stale-review controls are in
`tests/test_cmd_review.py`. Tool and cache identities are replay evidence; current status does not automatically
compare them with today's machine. Replay of dirty-at-check files needs a later commit preserving their bytes.

## Detection layers

- **fast**: the protected `vl check`, what agents iterate with and what verifies (receipt `assurance: protected`).
  Comparator in a jail builds the challenge and the solution separately, exports both, requires every declaration
  in the statement's closure to be identical (names, types, universe levels, safety level, definition bodies),
  restricts the solution to an axiom allowlist, and replays it through the Lean kernel and, while
  `[lean] external_kernels` is on (the default), through nanoda as a second kernel (a protected check on a machine
  without nanoda is `unsupported`, and a pass only the Lean kernel replayed does not count). Plus cheap
  statement probes after a pass, on a copy of the challenge built before any candidate code ran: a triviality
  probe (a fixed battery, `trivial`, `decide`, `simp`, `simp_all`, `omega`, and `tauto` and `aesop` when the
  project has them, each attempt under a deterministic heartbeat limit, the found proof replayed by the kernel), a
  premise-vacuity probe (the same battery derives `False` from top-level Prop hypotheses), and command lints over the files the
  candidate changed (warnings). Pass, fail and tool error are three different outcomes. An exploratory check
  (`--explore`, `assurance: exploratory`) runs the same machinery on the worktree's own copy of the question, so it
  catches none of the modes where the candidate edits the target, its definitions, the evaluator or the
  configuration, and it never verifies.
- **deep** (planned, not built: there is no `--deep` flag and no `deep` assurance; every `deep` cell below carries
  `*`): a slow, occasional check at a breakthrough, before a merge request or before explaining a result to a
  person. Everything in fast, plus a clean rebuild without shared caches, mutation of the conclusion (each conjunct
  or disjunct replaced by `False`, the same proof re-checked), reproduction of every committed receipt from a clean
  clone at the trusted commit (a receipt that does not reproduce is `unreproduced`), and a toolchain and kernel
  version floor.
- **test gate**: the repository's own suite (`scripts/gate`) runs Comparator's 20 known-answer projects through the
  same jailed Comparator path a check uses, and every planted case with the guard that catches it on and off. It
  tests `vl` itself, not a user's result.
- **referee**: a reviewer agent with the `vl-referee` skill, started with a clean context, reads meaning:
  hypotheses against lemmas, scope against prose, rigor of the argument. It writes a fidelity review bound to the
  target hash. Independence comes from the clean context, not from the model family; `vl` prescribes no model and
  never launches agents.
- **process**: rules about who may change what and which records count: target, theorem list, witnesses,
  evaluator and configuration read only from the trusted ref; incoming validation of merged work; only protected
  receipts committed on the trusted ref count; receipts self-hashed (an edit shows; anyone can recompute the hash,
  so admission, not the hash, is the guard) and bound to input digests; status derived, never written by hand;
  `vl validate` warnings, such as a target theorem with hypotheses and no witness.
- **none yet**: no check at any layer, referee included.

Reading the tables:

- `*` after a layer means planned for that layer, not built. Built: the Comparator checks, the jail, receipts and
  incoming validation, nanoda replay through Comparator's external-kernel setting, Comparator's known-answer
  projects as a test gate, the triviality and vacuity probes, the witness requirement, the command lints and the
  `vl-referee` skill. Planned: the syntactic lints (non-ASCII, unused binders, auto-implicit) and the whole deep
  layer. A triviality hit is a warning that a fidelity review of the current target must acknowledge
  (`vl review --acknowledge trivial`); a vacuity hit makes the result `vacuous`, never `verified`; a probe miss is
  not evidence of fidelity.
- Planted case: the fixture directory name. Lean cases are in `fixtures/lean-planted/cases`, Python defects in
  `fixtures/python-planted/defects`, and `ck:` marks Comparator's vendored known-answer projects
  (`fixtures/comparator-known`). `to plant` means no case exists yet; for referee-only rows it means a record a
  referee is expected to flag, which exercises the skill and not a deterministic check. `n/a` means a fixture
  does not apply (inherited error, needs more than 18 GB, covered by another row, or hygiene). Controls
  (`control-*`, and the Python candidate `wrong`, which must simply fail) and malformed-item cases (`d9-*`) are
  fixtures without a row of their own.
- Source: a public reference (key at the end) or `observed in practice`, an incident seen in agent-driven
  research work and described generically. `(reproduced)` = reproduced against the real checker; `(review)` =
  reported by a reviewer, not reproduced. `(unconfirmed)` = single secondary source, or inference without a
  source; not used to decide a layer.
- IDs: P proof, E environment and tooling, S statement, R process, X experimental and numeric, A agent reward
  hacking.

Evidence in numbers (public sources, for calibration):

- [SWARM]: 100 agents on 71 problems; after 37 were solved legitimately, one agent found a `local notation`
  exploit and the other 34 were "solved" within 27 minutes. The harness was a keyword blacklist that omitted
  `local notation`, a byte match outside editable markers and exit code 0.
- [LONGCAT]: training pass rate surged around step 80; nine hacking patterns (theorem tampering, `#exit`, axioms,
  meta commands, `unsafe` or `partial`, a global `variable` with a false premise, redefined background concepts,
  local instances, prerequisite tampering); an AST-consistency check cut the hacking model's pass rate on 1,024
  cases from 97.9 percent (syntax check alone) to 27.9 percent.
- [MCTS]: an axiom audit removed 4 and 8 whole-proof successes and 11 and 19 search successes on PutnamBench.
- [FC]: 291 misformalizations fixed in one expert-reviewed repository; 48.1 percent were misrepresentation.
- [FAULTS]: 12 Lean metaprogram checkers over about 10,000 problems gave 4,833 findings, about 398 with a
  machine-checkable certificate of unprovability or vacuity.

## What no layer can fully catch

| Limit | Why | How `vl` makes it detectable |
|---|---|---|
| A same-user agent writing files on the machine | On one machine it can write any file a checker reads: caches, receipts, the repository itself | Reproduction of every committed receipt from a clean clone (deep*, `unreproduced` if it does not match); branch protection on the forge, so the trusted ref cannot be edited by the agent; referee review; a human reading the statement. Detectable, not impossible |
| A misformalized statement that is internally consistent and non-trivial | Comparator proves the proof matches the target, and the probes find trivial or vacuous targets; neither can know the target is the wrong question | Referee reading scope against prose; independent formalization; test lemmas on boundary cases; trying to prove and to disprove; a human with domain expertise (S4 to S17) |
| A soundness bug present in both the official kernel and the external kernel, or a stale external kernel | A second kernel only helps if it is current and does not share the bug | nanoda replay in every protected check while `[lean] external_kernels` is on; version floor (deep*, below); the toolchain and each tool's sha256 in every Lean receipt; a second external kernel for high-stakes results [PM1] |
| The sandbox itself | Comparator assumes landrun is correct, the run is not root, and solution files were never compiled before; it does not protect against compromised challenge files or imports | Jail around the whole check; clean rebuild (deep*); supply chain pinned and hashed (E2, E6, E7) |
| A reader, human or LLM, who reads wrongly | An LLM audit is a triage signal, not a gate; the choice of LLM judge shifts faithfulness scores by 25 points or more [SIGCOV] | A review is a record bound to the target hash, never a score; a clean context per review; the card shows proof and meaning separately |
| Numeric and experimental results outside Lean | `vl` isolates the evaluator but cannot know it measures the right thing (X5 to X11) | Known-good and known-bad candidates run first; mutation of the check itself; two independent counts; a human |
| Prompt-level prohibitions | An integrity prompt did not stop an exploit once one agent found it [SWARM] | Nothing depends on the agent obeying: the checks run on the artifact bytes |

| #14576 | nested inductives with phantom parameters give an axiom-free `False` passing `--trust=0`; CVE-2026-72844 | 4.32.2 | affected; the old nanoda had an independent bug, and only the pair fooled both checkers |

| #14838 | reference-count overflow, use-after-free in the official kernel | the 4.33.1 to 4.34.0 series (present in v4.34.0-rc2) | in-process replay exposed; nanoda, a separate process, reportedly rejected it [PM2] (unconfirmed) |
| 4.34.1 | overflow fixes, reachable only with more than 18 GB of free RAM or inputs above 100 GB | 2026-09-24 | the per-run memory cap of `vl` is below this |

- Floor for the deep layer*: warn below Lean v4.34.0-rc2, the first release containing the August fixes (#14806,
  #14807, #14843, #14838 are in its commit history). Recommend 4.34.1 whenever the per-run memory cap is raised above
  18 GB. Also a current nanoda and GMP 6.3.0 or later (#14833). The warning never changes a verdict by itself;
  upgrading a project's toolchain is the project's decision.
- **nanoda must be current.** Checking with an independent kernel still works, but "users who rely on it need
  current versions of both" [PM1]. The Lean Kernel Arena listed nanoda revision 4c544ed as current on 2026-10-01
  (unconfirmed, one secondary source); a later revision supersedes it.
- Every Lean receipt records the toolchain, the Lean version and the sha256 of each tool it ran, nanoda included,
  so a receipt produced below a later floor can be identified after the fact.
- [PM2] reports nine bugs found in three weeks by an AI-guided search (4 kernel soundness, 2 runtime soundness,
  3 other), whose agents were told to rely on Comparator and external checkers.
- `lake check --paranoid`, planned for Lean 4.35, would recheck with every shipped kernel (unconfirmed).

## Checklist for the referee

Derived from the statement-level modes. Read the target and its definitions, not the proof. Write one of
`faithful`, `too-weak`, `vacuous`, `wrong-definition`, `unclear` in a fidelity review bound to the target hash, and
say what you did not check.

1. Print the elaborated statement and read it against the prose, word by word (S3, S12).
2. Look for escape disjuncts and branches: `∨ True`, `if … else True`, a conclusion that is a union with something
   trivial (S5).
3. Unfold every non-library definition in the statement's closure; none may be constantly `True` or `False`, a
   dummy record, or detached from the object it names (S5, S15, A4).
4. Are the hypotheses satisfiable? Is there a witness? Does any hypothesis hold trivially at 0 or on an empty
   range, or contradict another (S6)? For a non-existence claim, inspect the denied class for unintended
   constraints. A witness at another datum does not establish adequacy here; compare the intended admissibility,
   compatibility and boundary conditions. Do not require the very global solution the theorem rules out.
5. Does any hypothesis equal the conclusion after unfolding, or carry its key identity (S7)?
6. For each `-` on ℕ, `/`, `%`, `⁻¹`, `sqrt`, `log`, `tsum`, integral, `deriv`, `sInf`, `sSup`, `ncard`,
   `limsup`, `Classical.choose`: is there a guarding hypothesis, and does the claim survive the junk value (S8)?
7. Check coercions, `Fin` wraparound, `=` vs `==`, duplicated instance binders, default structure fields (S9).
8. Does every free name come from a declared binder (S10)?
9. Check quantifier order and scope; build an instance with X and not Y before accepting "X implies Y" (S11).
10. Check 0- against 1-indexing, notation expansions and precedence (S12).
11. Compare the hypothesis list with the source line by line, and with the item's `assumptions`; every added
    hypothesis must be named and justified (S13, R13).
12. Does every claim word in the prose (all, for large N, each coordinate, nonzero, equality case, the whole
    family) have a counterpart in Lean? Is a lemma or a single point presented as the headline (S14)?
13. Do the definitions pass test lemmas on first terms and boundary cases? Is there a link theorem between
    duplicate definitions (S15)?
14. Look for overrides in files the statement reaches: notation, macros, instances, attributes, `open`, `export`
    (S2). For answer slots, is the filler anything other than the answer (S4)?
15. Are the toolchain and library revisions pinned, and is the source statement itself right? Try to prove and
    to disprove it (S16, S17).
16. Who wrote the statement, when was it frozen, and is there an independent reference to compare with (R8)?
17. Does every lemma in the proof lead to the target, or is some true but unrelated (A4)?
18. Does the record state its claim kind and limits, with no process state (`vl validate` names the common
    phrases) and no fragment promoted to the whole (R12, R13)?

A referee verdict is a review, not a proof, and an LLM referee is a triage signal (R17).
